STOCKFLOW BANK ACCOUNTS DEPLOYMENT PACKAGE — REVIEW ONLY
Prepared 11 November 2026 for January 2027 policy

DECISION: DO NOT EXECUTE / NOT RELEASE-CERTIFIED

This package prepares production-target SQL candidates from the locally tested
implementation. It does not connect anywhere, apply SQL, grant permissions, change
configuration or activate anything. No database client or application was started
while preparing it. Only file generation and static consistency checks were run.

The candidate differs from the local migrations in its explicit target/approval
guards, runtime environment gate, explicitly qualified object creation and pg_temp-last
SECURITY DEFINER search paths (preventing temporary relation shadowing). Those
differences have NOT been executed in
a database. A production-ready release cannot be certified until the full-schema,
application connection and financial release blockers below are closed. This is a
review package, not authorization to deploy or an instruction to run 090-093 remotely.

JANUARY POLICY / FINANCIAL MODEL

 - One active operating account per tenant/business initially; inactive accounts
   and financial/audit records retained. No duplicate accounts for individual shops.
 - At most three active assignments per account initially. The existing many-to-many
   bank_account_shops relationship supports expansion without restructuring.
 - Private maintenance policy values max_active_accounts/max_assigned_shops are
   positive configurable data, defaults 1/3. They are installation-wide limits whose
   counts apply per business/account; no runtime policy-editor permission is added.
 - Authorized writer holds configuration/account/request locks and policy row SHARE
   lock, enforces limits on create/assign/reactivate and detects stale versions.
 - One account opening plus signed verified movements gives consolidated Recorded
   Bank Balance through the selected effective date. Unverified links add ZERO.
 - Money In/Out/Net exclude opening; movement counted once in consolidated totals.
   Owner shop filter uses that shop's allocations while whole-account balance stays
   explicitly labeled. Shop-filtered views omit running balance and full-event reversal.
 - Owner authority does not grant implicit bank permissions. Owner transaction
   read spans the tenant account; source linking/verification still validates source
   module permission and active business profile/scope. A complete cross-profile
   source-selection UX has not been established for release.
 - Shop Admin returns only active authorized shop/location/profile allocations;
   no opening, consolidated balance, running balance, foreign-shop options/amounts
   or shared batch total. Admin may not link, even with EDIT; linking is Owner-only.
 - Default change affects future choices only. Existing immutable links do not move.
   Current payment forms still lack inline receiving-account capture (see blockers).

OWNER-FIRST ACTIVATION — PLAN ONLY

1. After approved read-only discovery, identify the actual tenant_id and user_id of
   the existing Owner from trusted administrative records and verify users.is_tenant_owner,
   active user/tenant/role and real authorized shops. A role name, UI label, numeric
   ID from a synthetic database or caller-supplied tenant is NOT identity proof.
2. Verify coherent authentication/business/bank database, target schema, immutable
   financial history protections, protected keys and exact application release build.
   Current repository BankAccountsRepository is LOCAL-ONLY; do not enable this build
   against real identities pointing to the synthetic bank database.
3. Apply approved fresh-bank migrations in order during a separately approved
   maintenance window with backups and schema evidence. Check 40: all controls OFF,
   module inactive, no user/role grants, indexes/constraints and privileges as reviewed.
4. With separate permission-bootstrap approval, use existing authorization/audit flow
   to assign ONLY this Owner's existing actions needed for the agreed initial scope:
    VIEW — account list/transactions
    CREATE, EDIT — account configuration and Owner-only destination attribution
    ASSIGN — authorized shop assignments
    SET_DEFAULT — future receiving selection metadata
    DEACTIVATE — retire/reactivate subject to caps
    VIEW_BALANCE — Owner consolidated recorded balance
   VIEW alone is sufficient for a read-only pilot; add configuration actions only if
   that phase is approved. EDIT permits linking, so the configuration pilot is not
   wholly read-only even with bank posting OFF. Linking does not verify settlement.
5. Do NOT initially grant INITIALIZE, VERIFY or REVERSE. Leave VIEW_DETAILS and EXPORT
   ungranted: full-number reveal/export are not implemented. No new permission keys,
   blanket Owner/Admin grants or COMPANY_SETTINGS/REPORTS compatibility shortcuts.
   Existing SQL checks user_action_permissions; role templates alone do not grant
   effective access. SecurityRepository.WritePermissions/SetPermissionsAsync and
   SetRolePermissionsAsync enforce grantor restrictions. If nobody possesses a new
   bank action, prepare a separately audited, exact-Owner bootstrap change for review;
   this package does not bypass the restriction or supply generic grant SQL.
6. After separate activation approval, activate the BANK_ACCOUNTS module and required
   existing action metadata/catalog/route/profile mappings, refresh permission/session
   caches using the established process, and set the reviewed database configuration
   gate ON. Enable BankAccounts:Enabled only in the reviewed production-capable build.
   Keep BOTH BankAccounts:PostingEnabled=false and SQL posting_enabled=false.
   No executable activation file is included. Menu check: Business Setup > Bank Accounts,
   /Settings/BankAccounts and /api/bankaccounts with the intended Owner identity.
7. Verify direct API permission/CSRF denials, create/assign limits, masked details,
   failure behavior and defaults. An absent opening is uninitialized, not zero balance.
   Opening/verification/reversal must fail from UI, API AND direct runtime SQL.
8. Later authorize named Shop Admins with explicit VIEW and approved shop/location
   membership. Current SQL recognizes active role_name normalized to 'admin'; verify
   the target's actual role contract rather than renaming roles or adding a shortcut.
   Verify own activity only and denial of forced shop filters/foreign account IDs.
   Do not grant configuration, linking or VIEW_BALANCE to Shop Admins. Additional
   bank-evidence permissions require the separate financial phase below.

FINANCIAL POSTING ACTIVATION — SEPARATE APPROVAL

Do not treat installation/menu approval as permission to post bank money. Prerequisites:
full-schema regression evidence; reviewed source contracts; resolved same-UTR correction
policy; durable unknown-result recovery; protected key recovery; tested authorization,
duplicate/race controls and an agreed manual-verification operating procedure.

 - Independently authorize named verifiers with existing VERIFY; Owner/Admin status
   alone is insufficient. INITIALIZE stays Owner-only plus explicit permission;
   REVERSE has its own explicit approval. Shop Admin verification remains single-source,
   current authorized scope; shared verification/reversal is Owner-only.
 - Separately approve application AND protected SQL posting controls ON; neither gate
   replaces the other. Do not backfill or fabricate historical settlements.
 - Initialize each account ONCE against actual authorized bank evidence, amount,
   reference and tracking timestamp. Zero is valid if evidenced. Define same-day
   tracking boundary and evidence already included in opening to prevent double count.
   Opening is not a daily receipt; shop assignment must not duplicate it.
 - Link a genuine eligible existing payment once. Check tenant/shop/location/profile,
   source amount/direction/method and module permission server-side. Recording UPI/card
   means unverified destination attribution, not settled money or a live balance.
 - Verify actual bank credit/debit with reference/UTR, effective date, amount and
   explanation. Retain server timestamp, verifier, request identity and source/shop
   allocations. Signed allocations must exactly equal the statement movement.
   Current implementation does not invent fee adjustments or support fee-net batches.
 - Check exact retries, changed-payload conflicts, duplicate source/reference rejection
   and concurrent postings. Shared movement is one consolidated event; allocation
   projections supply shop totals. Verify absence of foreign-shop data from Admin APIs.
 - Reverse an erroneous verification by appending an equal opposite event/allocations;
   never edit/delete the original or undo the source payment. Current same-reference
   uniqueness blocks later re-verification of that SAME UTR: unresolved release blocker,
   not a reason to invent another reference. Opening correction is not implemented.
 - Verify redacted configuration audit and complete immutable movement/request history.
   No source customer/supplier balances, Cash in Hand, stock or GST should change.
