ROLLBACK / FAILURE CONTAINMENT

1. Preparation now: no database changes exist to undo. Do not run rollback/drop SQL
   against Remote merely because a package has been generated.
2. SQL error before a script COMMIT: ROLLBACK only its failed transaction; earlier
   committed package stages are separate. Inspect them read-only. Do not assume a
   rollback in another Query Tool session cleared this session or earlier commits.
3. Installation-only failure: keep all application/SQL gates OFF and module inactive;
   preserve committed foundation/metadata while reviewing. This is safer than dropping
   tables. An approved repair/resume must compare exact definitions first.
4. Configuration/financial activation rollback: under explicit incident/change authority,
   quiesce writers/stop new requests, resolve in-flight/unknown outcomes, disable
   application and SQL posting gates, then module/configuration entry as appropriate.
   Revoking a gate does not cancel an already-running transaction; drain/check them.
5. Return only to a schema-compatible application build with BankAccounts OFF. Leave
   account, opening, movement, request, allocation, ciphertext and audit history intact.
   Do not undo source payments/outstanding/GST/stock or delete verifications.
6. Wrong verification is corrected only by approved append-only reversal workflow;
   broader correction/reverification policy is an unresolved release gate.
7. Any destructive down migration, full restore, key restore or credential/config
   change needs separate approval and an impact/recovery plan. No DROP/down script
   is supplied. Full DB restore could lose unrelated business activity; never use it
   as an automatic Bank Accounts rollback. Protect retained keys with retained data.
