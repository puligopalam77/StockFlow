STOCKFLOW PRODUCT REGISTRATION ENHANCEMENT - 30 OCTOBER 2026

Result and identity contract
The existing four steps, order, panels, navigation and theme are retained.
Parent Product Code identifies a family. Variant SKU identifies a sellable stock
item. Barcode identifies that SKU or an individual tracked unit. These are separate
fields and relationships; searching a family returns its exact sellable variants.
New simple products receive one default SKU, normally <family-code>-STD, editable
before saving. Variant products retain one row per generated combination. Existing
product/variant IDs, codes, barcode mappings and transaction relationships are not
regenerated by this migration. Legacy Electrical default-item compatibility remains;
newly registered multi-variant families require an explicit SKU or tracked unit.

Registration changes
- Parent and dependent Subcategory pickers support search and bounded visible
  options. An active subcategory is required when the parent has active children.
  Direct assignment to an active parent without active children remains supported.
- Category/brand quick creation reuses existing authorized APIs, refreshes options,
  selects the created record and preserves wizard inputs/step. Applicable brands
  refresh after category creation. Brands retain category filtering/Show All Brands.
- Similar product names show an advisory; unique family codes, SKU and barcode
  ownership checks remain authoritative. Manufacturer part numbers remain separate.
- The Parent Product Code generator is explicitly labelled as a family identifier.
- Variant attributes support category recommendations, custom attributes/values,
  at most three axes, duplicate prevention and bounded combination previews.
  Configured required category fields retain their existing validation rules.
  Common specifications do not become variant axes automatically.
- Combination matching uses sorted attribute-code/value keys, rather than display
  names or row positions. Regeneration preserves matching edited SKUs, barcodes,
  prices, status and supplier mappings; removal of combinations requires a warning.
- The compact scrollable table exposes SKU, barcode, optional price overrides,
  status and actions. Saved variants are edited by their original IDs and are not
  deleted or recreated by the preview generator.
- Blank purchase/selling overrides inherit product defaults. Explicit overrides
  survive default changes. Legacy prices remain explicit until deliberately edited.
- Purchase costs are normalized before GST; selling prices use the configured shop
  tax mode. The entry checkbox describes the entered format. Stale tax-mode saves
  are rejected. Zero GST and existing tax/rate rules remain supported.
- Supplier searches use the existing bounded search endpoint with debounce/stale
  response handling. Preferred supplier is optional. Existing supplier identifiers
  now support expected cost, purchase unit, pack conversion and lead time. Duplicate
  supplier/code scopes and one preferred mapping per SKU remain enforced.
  New supplier mapping entry replaces duplicate free-code input; existing unassigned
  supplier references remain visible/preserved as legacy references.
- Existing verified vehicle text stays intact. New verified entries can link to a
  small shop/profile vehicle master, with product-wide and SKU-specific fitments,
  optional generation/variant, year range and notes. No legacy text is automatically
  parsed into assumed vehicle mappings. Vehicle lookup is searchable and bounded.
  Vehicle links remain separate from categories and product model names.
- Existing media gallery, main-image ordering, file limits, configured/custom
  specifications and warranty/provider support are retained. Image URLs must use
  HTTP/HTTPS without embedded credentials.
- Step 4 contains a compact review, catalog-only stock explanation and Save Product
  action. Success offers View Product, Add Another Product and Create Purchase.
  Registration during receiving asks which exact SKU to add for variant families.
- Barcode/SKU errors retain the form and show field feedback. Repeated submissions
  use a request UUID and payload hash; an identical retry recovers the original
  product, while a different payload cannot reuse that UUID.

Existing modules and APIs reused
Existing category, brand, supplier, product and variant APIs/repositories, category
attribute schemas, variant_barcodes, variant_supplier_identifiers, location reorder
settings, gallery storage, purchase/receipt posting, scan lookup and billing remain
the integration points. GET /api/products/vehicles is the small new lookup endpoint.
Variant searches now include family code, brand, category/parent category, supplier
references and linked verified vehicles. Purchase selection suggests supplier-specific
expected cost/pack metadata without rewriting confirmed or historical costs.
New SKU/parent-code conflict checks query matching records rather than fetching the
entire catalog. Supplier and brand entry reuse their existing masters.

Database/schema changes - migration 066
Requires 065. This is MANUAL ONLY and was NOT applied to the live application DB.
- products: registration_request_id, registration_request_hash, registration_defaults.
- product_variants: use_default_purchase_price, use_default_selling_price; existing
  rows default false, preserving every original explicit commercial value.
- variant_supplier_identifiers: purchasing_details JSON on the existing relationship.
- vehicle_models and product_vehicle_fitments: tenant/profile RLS, ownership/FK
  constraints, model identity uniqueness, product/SKU links and optional year/notes.
- Guards protect used family codes, stock units and SKUs; exact SKU selection is
  required for new multi-variant families at the API/resolver and SQL stock writers.
- Existing deferred category validation includes registered custom axes while
  preserving common-field validation and saved variant option identities.
No stock, purchase, receipt, sales, payment or historical price data is backfilled.
No SKU, barcode, variant or parent code is synthesized for old records.

Deployment and recovery
1. Stop application/workers and prevent other writers; take a fresh complete backup
   of the intended DB and verify a restore. The development backup is not a substitute
   for a current deployment backup after writers have been stopped.
2. Run 066_product_registration_preview.sql and inspect conflicts/missing identities.
   Resolve products without SKUs manually; the migration refuses to invent them.
3. Apply ../migrations/066_product_registration_integrity.sql as PostgreSQL superuser,
   after 065, with ON_ERROR_STOP. Deploy the matching application build together.
4. Re-run the preview and compare identity/value/ledger fingerprints. Verify product
   registration, exact-SKU selection and permissions before restarting workers.
5. On a failed migration, its transaction rolls back. For recovery after success,
   stop writers and restore the complete pre-066 backup into a separate database,
   verify identities, transactions and stock, deploy the prior application version
   and switch its connection only after reconciliation. Do not overwrite any new
   post-deployment transactions blindly. There is no destructive automatic downgrade.

Limits / remaining operational checks
- Apply 066 before using the enhanced save contract. Live authenticated browser
  end-to-end verification and physical printer/device testing remain deployment checks.
- Five missing legacy family codes need a reviewed correction if codes are required
  for those historical products. Existing SKUs continue working; no migration is
  required to invent replacement stock identities.
- Receipt quantities retain the existing stock-unit contract: 3 packs of 10 pieces
  must be entered as 30 pieces. Pack metadata does not silently multiply stock or
  recalculate historical movements when product settings change.
- Unsupported batch/expiry tracking modes and new return/service workflows were
  not introduced. Existing supported tracking, warranty and transaction rules remain.
- Existing common specifications remain common during SKU-specific vehicle-link
  editing. Old text-only fitment entries are preserved and are not guessed into
  verified master records. The vehicle master is managed through product fitment
  entry/search, without a new sidebar module.
- Newly added defaults do not retroactively reinterpret legacy explicit variant
  prices or historical transactions. Existing barcode values are retained.
