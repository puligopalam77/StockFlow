STOCKFLOW
Super Admin Integration: Source-backed Blueprint Review
03 November 2026 | Review and expanded design only | No implementation or deployment

Prepared for the StockFlow product owner and engineering team. This report reviews the supplied 25-section architecture blueprint against selected current repository source, migrations and recorded verification artifacts. Proposed controls in this report are recommendations, not implemented capabilities or authorization to change the application.

1. Executive assessment

StockFlow should add a platform administration layer around its existing retail application, rather than rebuild billing, inventory, profiles, GST, permissions or Expenses. The strongest immediate scope is secure tenant onboarding, an operational tenant directory, privilege-separated administration, recovery evidence and controlled support. Commercial entitlements and subscription billing should follow as separate tested slices.

The reviewed application already contains substantial tenant/shop foundations: tenant-owned users, store/location assignments, restricted database connections, RLS, granular permissions, shared sessions, four business profiles, private-shop master ownership, explicit sharing, GST registrations, notification workers and an Expenses workflow. These are integration points, not missing modules to recreate. [E02-E12]

No dedicated platform-admin portal, platform role catalogue, tenant provisioning business workflow, global human-to-tenant membership model, subscription lifecycle, commercial entitlement engine or approved support-access workflow was found in the reviewed source inventory. Text saying "Contact Super Admin" in StockBot is not evidence of such a portal. Treat these as new platform capabilities requiring design and negative authorization tests. [E01-E04, E13]

The supplied supplement is cautious but out of date in several places: Expenses F04 and private-shop controls were implemented after the earlier audit baseline; the recorded synthetic recovery test now covers 148 public tables, including expense/payment/receipt evidence; the referenced candidate has 25 automated passes, not 23. That candidate still has nine unverified manual gates and remains BLOCKED. These historical results do not certify the source reviewed today or any production environment. [E08, E09, E18]

Three high-impact design constraints must shape the integration: Admin is currently MFA-exempt; users currently belong to one tenant; and the active business-profile choice is currently tenant-wide. A new Super Admin must not inherit the retail Admin role or assume those future identity/profile capabilities already exist. [E03-E06]

Recommended outcome: one maintainable application with a separately authorized platform control plane; ordinary retail operations continue through the existing scoped services. A separate portal hostname or process may strengthen the boundary, but a different URL alone provides no privilege isolation. Keep deployment authorization and irreversible ownership/costing decisions explicit.

4. Current architecture and integration seams

The web application targets .NET 10 and uses Razor Pages, API controllers, application interfaces/services, Dapper/Npgsql repositories and PostgreSQL migrations. This structure supports a modular platform area without cloning the retail application. Shared application code does not require a shared elevated database role. [E01, E02]

Existing request flow: authenticated cookie and session validation; BusinessScopeMiddleware resolves TenantId/user and validates active tenant/user/role plus store/location membership; PermissionMiddleware checks security version, password/MFA requirements and module/action access; repositories open a scoped stockflow_runtime connection; RLS and guarded writer functions enforce database rules. Consolidated views are distinct from a single posting location. [E02-E05]

The future platform request flow must be separate: platform authentication and fresh MFA; platform permissions; target-resource authorization; approved command; immutable platform audit; then a narrow control-plane repository/function. It must not synthesize an ordinary owner's cookie, set IsOwner=true, or pass arbitrary tenant/store values into the retail factory. A tenant owner must never acquire platform powers by editing a tenant role.

Database roles should be split by purpose: retail runtime; existing notification worker; proposed limited platform-control role; separately approved support role; and offline migration/DBA credentials. Platform control functions should manage lifecycle/configuration metadata without blanket SELECT on sales/customers or unrestricted SECURITY DEFINER SQL. Do not use superuser or BYPASSRLS for normal platform HTTP traffic.

Tenant, shop, location, profile, legal business, GST registration, human identity, subscription and provider sender are separate identifiers. A tenant may contain independent private shops; the approved model does not force them to be merely branches of a single legal business. Shops mapped to the same GST registration may require specifically authorized reporting without sharing every contact/catalog record. [E04, E07, E08]

6. Priority additions: complete lifecycle behavior

6.1 Tenant provisioning and invitations

Use a durable provisioning request key and explicit states: Requested, Validating, Provisioning, AwaitingOwner, Ready or Failed. Persist completed steps so retries resume safely. Create a unique tenant, private shop/location, scoped roles, owner invitation and safe initial configuration without copying another tenant's data, tokens or contacts. Do not send reusable default passwords. An expired invitation must be renewable without making a second tenant. Record who verified ownership and which setup steps still require shop evidence.

Use existing BranchRepository for branch/location behavior within an authorized tenant; do not call it with a fabricated owner scope from a general platform request. A future orchestrator needs narrow approved provisioning commands and compensating actions for partial failures. Provisioning is distinct from enabling paid entitlement. No test fixture seed or migration 020's DEFAULT tenant should become a customer onboarding template.

6.2 Tenant lifecycle, suspension and closure

Current is_active checks provide part of the enforcement foundation, but a single Boolean is not a full lifecycle. Define Draft/Trial/Active/Grace/Restricted/Suspended/Closing/Closed states, their transition authority, effective time and permitted operations. Security suspension differs from unpaid subscription restrictions; neither should rewrite invoices or erase customer history.

Specify behavior for new login, existing sessions, checkout already in flight, held drafts, import jobs, queued notifications, webhooks, exports and refunds/returns. Revalidate at job execution and define a safe transaction boundary: a feature switch cannot cancel a committed sale or justify duplicate retries. Provider callbacks may still need to record acknowledgements after sending is disabled. Preserve read/export/support/recovery paths according to the agreed policy.

Closure is an approved process with export, outstanding operational obligations, retention/hold review and scheduled deletion where applicable; it is not a DELETE tenant cascade. Reactivation must restore only approved entitlements, not old expired support grants. Platform-owned lifecycle events need reasons, actor, request key and before/after state.

6.3 Identity, MFA and account recovery

Introduce a platform permission vocabulary independent of tenant Admin: TenantRead, TenantProvision, LifecycleManage, EntitlementManage, BillingReview, SupportGrantReview, IntegrationManage, AuditRead and RecoveryReview are conceptual examples, not current actions. Use separate privileged sessions/cookie scope, shorter expiry, fresh step-up for dangerous actions and revocation after permission changes. Do not reuse the Admin MFA exemption. [E03]

One human spanning multiple tenants should be a later identity-linking slice: global identity plus tenant memberships that map to existing tenant user IDs. Require verified account-linking; never merge users merely because their email/phone matches. Preserve created_by/audit references. A context switch must reauthorize membership, reset shop selection, terminate stale pending writes appropriately, clear scoped caches and keep drafts bound to their original context. Tenant owners may legitimately see their own authorized stores, not every tenant owned by someone with the same email.

Owner transfer, lost MFA device and platform-admin recovery require an explicit verification trail and a second authorized approver for high-risk changes. No platform staff member should reset their own privilege or grant themselves customer access. Break-glass access is separate, time-bounded, alerted and reviewed afterward.

6.4 Customer-approved support

Prefer diagnostic metadata/redacted identifiers before content access. A support request records tenant, allowed shops, issue/ticket, purpose, requested fields/actions, approver, start, expiry and session binding. The tenant can inspect and revoke it. Support must not default to retail posting, raw SQL, unrestricted downloads or token visibility.

Every data access/export under a grant should be attributable to the real support actor, never only the impersonated owner. Revocation/expiry must apply to subsequent API calls and running jobs, including generated downloads. Financial corrections remain the existing authorized shop workflow with its normal reasons and audit. Platform staff cannot silently repair amounts by updating tables.

6.5 Subscriptions, quotas and reconciliation

Use separate SaaS invoices, customer-account subscriptions, provider payment attempts, webhook inbox, entitlement snapshots and reconciliation records. A signed webhook is necessary but alone does not prove the correct account, amount, currency or final settlement; verify event identity and business invariants. Handle duplicates, late/out-of-order events, refunds, chargebacks and renewal overlap idempotently. Do not post StockFlow subscription revenue into a shop's sales table or expense payment ledger automatically.

Approve the commercial policy before code: plans, price/tax treatment, free trial, user/shop counting, renewal time zone, grace, downgrade, cancellation, refunds and read/export-after-expiry. Retain historical documents when a feature expires. An over-limit existing tenant should receive a clear restricted-write state rather than silent deletion or inability to settle existing work.

Quota basis must be explicit: active named users versus sessions; owned active products versus shared visible products; source imports versus created rows; AI requests/tokens/time; message attempts versus accepted/delivered messages; attachment bytes retained versus uploaded. Enforce atomically with a scope, period, idempotency key and reconciliation. Do not label the existing WhatsApp daily attempt counter a global subscription/billing quota. No invented monthly limits or unlimited provider claims.

6.6 Deterministic entitlements and flags

Availability, entitlement, rollout, authorization and business validation are separate. Recommended new-write decision: authenticated scope AND active authorized context AND compatible deployed capability AND lifecycle policy permits operation AND tenant entitlement AND shop enablement AND rollout permits behavior AND user permission AND profile capability AND resource ownership AND business rules. Entitlement can restrict access but never grant permission or make an unsupported industry ready.

Define a separate historical-read/export decision; one AND expression that hides old invoices after expiry is unsafe. Explicit emergency deny should win for the affected operation; finite overrides expire; inherited plan grants must be inspectable; no dependency cycles. Return a safe user-facing denial reason and decision version. Retail pricing/tax results must continue to come from current billing services and saved snapshots, never the flag engine.

Record the evaluated version for mutations/jobs, set bounded cache lifetimes, invalidate on urgent revocation, and test stale sessions. Capability state must account for deployed adapter and schema support, not just a visible menu/module row. A migration-required control should fail closed with a clear setup state. New framework integration must not accidentally miss Razor POST handlers, files, background workers, exports or SECURITY DEFINER entry points.

8. PostgreSQL and data governance design

Reuse tenants, stores, store_locations, users, roles, modules, module_actions, user/role action permissions, user_store_access, user_location_access, auth_sessions and the existing GST entities. Do not introduce illustrative blueprint aliases such as legal_entities/tax_registrations as duplicate replacements for gst_legal_businesses/gst_registrations. Modules currently form a permission/navigation vocabulary, not a paid-plan catalogue. [E02, E04, E07]

Conceptual additions, subject to later approved design: platform_principals/roles/assignments; tenant_provisioning_requests and invitations; tenant_lifecycle_events; plan_versions/subscriptions/billing_events; entitlement_versions/shop_capability_assignments; feature_definitions/overrides; support_access_requests/grants/access_events; operational_incidents; deployment/schema evidence; export_jobs and retention/hold decisions. Names are suggestions, not existing tables, migrations or APIs.

Each control command should have actor identity, target tenant/shop, permission, expected version, idempotency key, reason, effective time, correlation ID and result. Immutable events and a current-state projection support investigation. Audit should record evidence hashes/references while excluding passwords, tokens, message contents and attachment payloads. Retention and tamper resistance require a policy and tested storage controls; a table named audit is not sufficient.

085 is additive but still requires an approved real-data migration review. Only exactly-one-store tenants get automatic legacy allocation; multi/no-store records remain NULL-owned. Existing SKU/barcode/code namespaces remain tenant-wide. Cross-tenant template distribution should copy approved metadata into fresh tenant/shop IDs, not share live retailer rows. Retain source-template/version provenance and existing validation.

Per-scope connection-string Options create distinct Npgsql pools; MaxPoolSize=10 is per distinct pool, not an application-wide ten-connection cap. Capacity planning must measure tenant/user/store cardinality, connection peaks and job pools. Test alternating contexts, reused connections, failures, cancellation, readonly consolidation and raw SQL helpers. A future transaction-local context redesign must be explicit and separately verified, not assumed from the blueprint. No pool or DB-role change is made here.

9. Reliability, recovery and operational coverage to add

Public /api/health is liveness only. /api/database/health and /api/database/operations are permissioned tenant operational checks; the latter reads a server-mapped private recovery evidence file and probes selected capabilities (082/083), not every applied migration/checksum. Extend with a real schema/deployment inventory for 084/085/086 and future releases; never label a capability probe a verified full migration history. [E11]

Existing backup/scheduler/restore scripts are assets to reuse, not an absent recovery implementation. Platform operations should show last successful archive, schedule/failure alerts, offsite replication, retention, most recent isolated restore and exactly what was restored. Recovery of a shared database is not automatically a safe single-tenant restore: validate tenant filtering, dependencies, roles, files, keys and reconciliation before offering tenant-level restore. Restoring over production requires separate authority.

The 148-table synthetic result proves that fixture's database digests and selected restricted app reads, including an expense/payment/PDF, survived restoration. It does not prove offsite credentials, application assets, actual login, current production recovery, RPO/RTO or historical data correctness. Preserve the evidence scope in the dashboard. Record operator, archive identity, source build/schema, destination isolation, timestamps, measured durations, validation results and expiry. [E18]

Add measured service-level indicators for login/checkout availability, DB latency, queue oldest age, unknown provider outcomes, certificate expiry, disk/storage saturation, AI pressure, export/import completion and backup age. Use per-tenant dimensions internally with minimal public detail. Platform alerts need routing, acknowledgement, escalation, resolution and deduplication, not just red tiles. Do not load retailer amounts/PII into general metrics labels.

Notifications and WhatsApp already use durable guarded functions and execution-time checks; preserve those fences. The future job registry should carry tenant/shop/sender/context, operation identity, payload version, entitlement version, attempt state and cancellation policy. Unknown remote outcomes require reconciliation rather than blind retry. Webhook acknowledgement and records retention must continue when outbound messaging is paused, subject to the defined security policy. [E12]

Shared Data Protection keys exist in database-backed storage. Losing/deleting keys can invalidate sessions or make encrypted sender credentials unusable. Review envelope/key-at-rest protection, backup access and rotation/recovery procedures with the actual host; source storage alone does not prove a secure deployed key vault. Separate application secrets, tenant provider tokens and human passwords in access/audit/export policies. [E05, E12]

10. AI governance and future Product Auto-Fill

StockBot's provider is Ollama; configured model is qwen3:4b at the local loopback endpoint. The provider selects approved help sections and interprets structured business queries; authoritative amounts come from scoped application services. The local worker can start an already installed runtime and sets OLLAMA_NO_CLOUD=1. This is configured behavior, not proof of model availability on each deployed server. [E13]

Current HelpModelGate allows one model lease per application process, and the account question gate/cooldown uses IMemoryCache. These limit contention locally but do not provide cluster-wide tenant fairness, durable commercial usage accounting or distributed limits. HelpTelemetry intentionally avoids raw questions/answers/audio; add safe tenant-associated aggregate metrics without turning support logs into a customer-data warehouse.

Proposed AI operations: approved model registry and version/hash, endpoint allowlist, dependency health, queue budgets, tenant quotas, per-use timeout, fallback/error rate, prompt/content minimization, evaluation datasets and opt-out. Product suggestions should have a separate schema and request budget; preserve StockBot/manual wizard availability under contention. No model-generated SQL, prices, stock, tax applicability, HSN/GST decisions or automatic saves. Human review and existing product APIs remain authoritative.
