Before onboarding additional paying shops, the deployment owner must:
1. Record the actual machine/service, database and persistent asset locations,
   HTTPS endpoint/certificate, process restart policy and secret recovery owner.
   Demonstrate reboot/restart recovery, database failure alert and redacted logs
   without exposing private readiness endpoints to ordinary users.
2. Agree an RPO target (maximum tolerable age of recovered committed data) and RTO
   target (elapsed time from recovery start to usable, validated shop operations).
   Values remain NOT AGREED here; synthetic elapsed time cannot select business
   recovery objectives. Set schedule/retention/offsite cadence to the agreed RPO.
3. Execute the actual scheduled backup under its service identity. Retain last-run
   timestamp/result, manifest/hash and a supervised failure alert. Verify encrypted,
   access-controlled offsite copies and retention. Restore from the offsite copy.
4. Include uploads/logos/attachments, deployment build/configuration, PostgreSQL
   owner/runtime roles and versions, Data Protection keys, and required encrypted
   provider credentials/secure recovery procedures. Never put plaintext secrets in
   this report, logs, task command arguments or public web directories.
5. Restore into a clean, access-controlled environment with required secrets and
   assets using production-strength authentication, rather than this trust-auth
   synthetic harness. Run database verification and start the restored app build.
   Confirm staff login and scoped customer/product/invoice/attachment access.
6. Reconcile known pre-backup sales, collections/refunds/dues and signed stock
   movements to recovered source documents. Record missing committed-data cutoff
   versus backup snapshot for observed RPO; record time to completed validation
   for observed RTO. Compare both to the agreed targets; preserve failure evidence.
7. Demonstrate approved same-profile/different-profile shop behavior with the real
   deployment topology. Existing tenant/profile-shared masters remain a release
   design gate; no destructive repartition or approved-independent-shop claim.
