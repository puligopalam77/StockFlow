# Product registration review

Apply `064_product_registration_review.sql` manually after 063, with a backup and the application/workers stopped, then restart. Existing product/variant IDs, SKUs, barcodes, stock, receipts and sales history are retained. The migration adds separate parent product codes and detailed descriptions; it also permits bike-accessory warranty defaults while retaining the existing electrical-only serial tracking rule.

The four registration steps remain:

1. **Basic Details:** live Category Master cascades, brand filtering, product code, model, unit, tracking, part number, status and short description. A single root with children is shown read-only. Further category selectors show only immediate children, and the final category ID is saved. Active categories whose parents are unavailable cannot be chosen. Brand Master supplies active choices; Show all brands explicitly confirms a category-association exception, which the server validates. No Generic brand is invented.
2. **Variants & Attributes:** configured category axes and specification fields replace the fixed Size/Color/Model/Material/Style list. When a category has no configured axes, users may add up to three product-specific variant attributes and their values. Category changes warn before removing generated combinations. Generated rows retain individual selling/purchase reference prices, MRP, reorder level, warranty duration, part number, supplier code reference, status and barcode identity. Barcode choices are Assign later, Existing manufacturer barcode and Generate internal model barcode (permission required). These shared model codes are distinct from the unique physical-item labels managed under Purchases > Barcodes. Vehicle compatibility is an optional section within this step.
3. **Pricing & Stock:** default prices, GST, MRP, pack quantity, reorder level and supplier information. Stock unit is read-only because it was selected in Basic Details. Changing defaults updates generated variants that have not received their own price override. Warranty months/provider are optional here; zero months means no warranty. Opening/received quantities stay outside registration. Supplier-specific identifier pairs remain available for a single variant; distinct supplier mappings for generated variants can be managed in the existing variant editor.
4. **Media & Specifications:** image gallery, optional image-to-variant association, image URL, a separate detailed description, category specifications and custom specifications. The first image remains the main image for existing stock screens. Existing image count/type/size checks remain in force.

Parent product codes are distinct from sellable variant SKUs and unique within the shop/tenant, ignoring case. New codes and SKUs have a 40-character limit; existing longer SKUs remain editable through the existing variant editor. The product code does not replace an existing stock identity. Existing products without a parent code are not backfilled.

Inactive draft products can be registered with zero prices and inactive variants. The existing sale validations continue to reject unavailable/inactive or improperly priced items. Active master references, brand exceptions, SKU/barcode conflicts, duplicate combinations, MRP, units, warranty and images are checked on submission. A stock transaction is never created by product registration.

Fitting settings are not collected in Product Registration. Fitting charges remain a Sales & Billing concern, as requested in the supplied recommendations. This change does not add or alter fitting billing transactions.

Validation: build MasterDataChecks and run `--product-review-checks`, then run `product-review-offline.cjs` using the Playwright Node runtime. The browser fixture uses the actual Razor screen and mocked APIs; it covers cascading masters, category axes, separate prices/barcodes, descriptions, warranty, image associations and mobile layout. `--retail-phase56-checks` covers existing exact-variant purchase, adjustment, quote, billing, transfer and invoice contracts. Migration 064 was exercised in a separate disposable PostgreSQL database for per-tenant code uniqueness and bike warranty/serial rules. The application database was not modified.
