# GST catalog tax configuration

## Prefilled imports and compact Step 4 (November 2026)

This update needs **no new SQL migration**. It reuses the schema and operations from 073; installations already through 076 need only the application update/restart. The configured application database was not migrated during development.

Step 4 opens Product Tax Mapping first, followed by Tax Rules and Billing Defaults. A compact progress strip replaces the four large status cards; it describes mapping coverage, not statutory compliance. Search debounces, filters apply immediately, Reset clears them, and subcategories/brand/advanced filters stay under More Filters. Changing filters clears selection explicitly. The six-column table retains View Tax Details, Edit Mapping and history. Header/row checkboxes show a selection bar only when needed; selection can span pages or explicitly include all matching backend results. Import and Assign Tax are the main actions; exports, operation history and eligible resume actions are under More.

**Import → Download Import Template** offers real Excel and CSV files containing all active products in the current shop/business-profile catalog, or all filtered matches. Downloads include every matching page, up to 50,000 rows. Choose product defaults or sellable variants. ProductId, optional VariantId, actual ProductCode, ProductName, ProductSku and optional VariantSku are already filled; no manual product lookup is required for a 2,000-item catalog. IDs/SKUs remain text in Excel, preserving leading zeros. Tax columns start blank, with no inferred HSN/rate or sample statutory classification. Excel includes a separate instruction sheet.

Keep identifiers unchanged and fill **RuleId** from an active reviewed rule in this shop (the Tax Rules tab shows rule IDs). HsnSac, Treatment, TaxRate, PricesIncludeTax and ReviewReference can be blank to use that rule's saved values; any provided value must agree. Blank EffectiveFrom uses today or the reviewed rule's start, whichever is later; blank EffectiveTo uses its end. Explicit dates must fit the reviewed rule. A rule still requires reviewed classification/evidence; this is not a free-form percentage import. Product/variant identifiers, active membership, duplicates, conflicts and override permissions are checked again by the backend. Both product-default and variant rows can appear in a file.

The visible upload dialog supports Browse Files, native file input, drag/drop, filename/size, Change/Remove and a disabled Validate File button until a non-empty CSV/XLSX of at most 10 MB is selected. Validation uploads actual multipart file contents to the existing endpoint, parses safely, and produces a saved preview without applying mappings. Preview shows the shop, filename, affected product/variant summary, current/proposed tax rules and effective dates; rows can be filtered by valid, review or invalid/failed status. Error/result reports are downloadable. Only READY rows are applied after acknowledgment and **Confirm Import**; unchanged/review/invalid rows are explicitly skipped. Existing recoverable 100-row commits and idempotent confirmation remain in use. Completed results refresh catalog counts and retain the active filters.

Export opens a separate scope/format dialog: all, filtered, selected or missing/review/expired/conflict rows; CSV or Excel. It never silently exports only the visible page. Billing Defaults still save the existing business-profile default, and wizard Save & Continue saves a changed billing default without committing an unconfirmed import.

Verification executed against disposable local PostgreSQL clones: prefilled CSV/XLSX downloads containing 2,000 products; real authenticated multipart uploads for both formats; missing/unknown header and corrupt/empty/unsupported file handling; strict identifier/rule/price consistency; permission/shop isolation; preview without mapping changes; and a complete 2,000-row import across twenty 100-row batches with repeated confirmation. The representative full import check took 41.77 seconds including seeding, templates, real upload previews and commit; this is a local diagnostic, not a service guarantee. Existing dated-rule, POS resolver, audit, stale-preview and financial/SKU/stock preservation checks passed. Browser checks covered ten specified viewports, native file chooser, drag/drop, visible validation errors, selection, preview, confirmation, results and exports using mocked APIs. Physical Windows 150% scaling/device acceptance remains a deployment check.

## Scope and reused behavior

GST Settings Step 4 now has Billing Defaults, Tax Rules and Product Tax Mapping tabs. Steps 1–3 and 5 retain their existing forms and activation flow. The old per-product tax form remains available through Edit Mapping → Individual Tax Version. The default catalog view contains one row per product; a paginated sellable-variant view distinguishes inherited defaults and overrides.

This extends `gst_tax_configurations` and the existing POS tax resolver. It does not introduce a second tax calculator. Company billing defaults, GST validation, role permissions, row security, invoice snapshots, source tax reports, shared compact action icons, confirmation dialogs and list pagination are reused.

## Required SQL

Apply **`database/migrations/073_gst_catalog_tax_mapping.sql`**, manually, after 072. Follow the file's backup, writer-stop and PostgreSQL-superuser instructions and run the entire transaction. Application databases were not modified during implementation; database tests use disposable clones.

The migration adds shop-scoped reviewed tax-rule versions, optional shop/variant/rule identity on existing product tax versions, audit metadata, recoverable operation headers/rows, permissions and catalog indexes. It does not backfill product classifications or alter prices, SKUs, barcodes, quantities, historical invoices or tax snapshots. Existing profile-wide tax versions remain historical fallback records. New mappings are scoped to the selected store/profile. Once a shop/variant has explicit applicable mapping history, expiry does not silently reactivate an older fallback.

The migration patches the existing configuration guard and sale-capture resolver using checked definitions. It aborts transactionally if the expected source function has been customized. Tax arithmetic remains unchanged; new snapshots also identify the rule and variant used.

Rollback before commit is transactional. After deployment, retain the added history and use reviewed prospective corrective versions. Do not drop rule/operation tables or remove mapping identities as a data rollback.

## Implemented workflow

- **Billing Defaults:** saves only the existing profile's `DefaultTaxMode`, under Business & Billing authorization, preserving other settings and logging the change. The tab states that this is a business-profile default, not a separate physical-branch default. Product prices and prior invoices are not rewritten.
- **Tax Rules:** server-paginated search; named classification/conditions, HSN/SAC, goods/service, treatment, numeric rate, UQC, cess, reverse charge, pricing, validity dates, reference and notes. Drafts can be edited. Explicit review records the authenticated reviewer and timestamp. Reviewed classifications are immutable; new non-overlapping versions preserve them. Authorized prospective end dates also end linked mappings, with audit records and an explicit warning that replacement configuration is needed.
- **Catalog:** server-side trimmed partial search over product name/code, product/variant SKU, HSN, parent/subcategory and brand; category, multiple-subcategory, brand, treatment, rate, status and effective-date filters; name/code/status sorting; shared 10/25/50/100 pagination. Settings requests omit the entire catalog. Searches debounce and filter changes apply automatically, clearing potentially stale selections.
- **Readiness:** Configured, Needs Review, Missing and Expired are derived from applicable versions and supported issuance conditions. Conflicting periods are blocked by database guards. The Conflict filter remains available for the status vocabulary; ordinary writes cannot create overlaps. The compact status strip summarizes the current product/variant view, not an invented tenant-wide total.
- **Bulk assignment:** select visible rows, retain explicit selections across pages, or confirm all matching backend results. Changing the filter/tab clears a potentially stale selection. A saved preview records actual targets, shop, product/variant counts, categories, HSN diversity, existing overrides/classifications and proposed rule conditions. It separates READY, MATCHING, REVIEW and INVALID rows. Users acknowledge applicability and confirm before writes.
- **Commit/recovery:** operations process at most 100 rows per request, with a configuration lock, per-row validation/savepoints and saved results. Repeated confirmation cannot apply a row twice. Stale product/mapping fingerprints fail rather than overwrite intervening changes. Changed reviewed mappings require override permission and a reason. Existing variant overrides remain independent of product defaults. Operation History and Resume expose the current user's saved operations within the selected shop/profile. Results/error CSVs remain downloadable.
- **Import/export:** CSV and data-only XLSX templates and exports; all/filtered/selected/needs-review scope through the catalog filters and selection. Imports accept up to 10 MB and 50,000 rows, use stable product/variant IDs, and validate SKU, rule, HSN/treatment/rate/reference consistency, duplicates, dates, permissions and shop scope before the same preview/commit workflow. No product creation occurs. Formula cells, macro/external-link workbooks, malformed CSV and oversized files are rejected; exports escape spreadsheet formula prefixes. Imports keep per-row failures and do not partially overwrite rejected rows.
- **Single mapping/history:** reviewed-rule assignment or the original individual classification fields, including pricing and advanced treatments. Existing shop versions can receive prospective end dates. History shows prior versions, dates, staff, references and reasons. Legacy profile records cannot be silently edited into another store's ownership.
- **Product registration:** the existing four steps remain. Authorized GST editors can search current reviewed rules during registration. Selection fills the visible HSN/rate for review; the backend validates the selection and saves its mapping inside the normal product registration transaction. An existing reviewed mapping is not destructively replaced from product editing. Historical registration-request hashes remain compatible when the optional rule is absent.
- **Checkout/reports/purchases:** checkout resolves the dated variant override before the product default, then an eligible legacy fallback, and captures the existing immutable invoice facts. The old generic product-rate function remains compatible. Purchase receipt arithmetic and supplier invoice registers retain their existing source facts; mapping changes do not infer ITC eligibility or rewrite supplier documents.

## Authorization and isolation

Existing GST_SETTINGS VIEW/EDIT protect access and ordinary maintenance. Migration 073 adds APPROVE_TAX, OVERRIDE_TAX, BULK_TAX, IMPORT_TAX and EXPORT_TAX; tenant owners receive them, while role defaults are denied. The permission catalog and API middleware expose/enforce them, with repository and database checks as well. Billing mode changes use COMPANY_SETTINGS EDIT.

Rules, new mappings and operation recovery are store/profile/tenant scoped. Catalog membership continues to use StockFlow's existing tenant/business-profile product model; this enhancement does not create independently duplicated catalogs for physical branches that already share a profile. Operational tax assignments remain store-specific. Sharing a GSTIN does not authorize cross-store operation recovery or share new mapping records.

## Remaining boundaries

- No official HSN classification dataset is installed. Format checks and an administrator's reviewed evidence do not constitute authoritative classification or GST Portal verification.
- The existing checkout still blocks services, zero-rated issuance, reverse charge and cess that require additional verified calculator support. Such rules can be recorded for review but are not presented as checkout-ready.
- Existing checkout pricing overrides must agree with the bill price mode. Mismatches are shown as requiring review instead of introducing new arithmetic.
- XLSX interchange is intentionally data-only and uses the template's first worksheet. It is not a general Excel editor.
- Large operations are resumable request-driven batches, not a new background-job service. If the browser stops, a user resumes the saved operation.
- GST filing, automatic ITC determination, multi-registration consolidation and broader accounting remain outside this change. Practitioner review remains necessary before using working reports/documents in production.
