UI
The logical and visual order is Customer, Scan/Search, Bill Items, Bill Totals,
Payment Method, completion, then Notes. Numbered section banners are removed.
The existing controls use the available content width in a white, rounded POS
workspace. Desktop (1000px and above) places customer/search/cart on the left
and totals/payment on the right. Checkout height adapts to viewport height and
updates on resize and heading changes, without shrinking the whole page.
The completion action and notes remain outside the scrolling checkout details;
a pinned More Billing Options action opens the existing options panel. Long item
lists and checkout details scroll independently. Below 1000px the same controls
return to their single-column reading order. Only this POS page hides the desktop
application footer to reserve working space.
The header shows a pink Draft pill and the existing draft UUID's short reference.
It never reserves a final invoice number. Completed sales change the status.
Hold, Saved Bills and Back to Sales remain available.
Customer opens a single search/selection disclosure. Add Customer uses the
existing registration dialog from within the picker and preserves the bill.
One search field has barcode/search icons and a compact camera action.
Bill rows have Product | Qty | Total, registered images or a neutral package,
exact SKU/variant/unit information, available stock, quantity stepper and trash.
Authorized price and discount fields plus tax remain in expandable Item Details.
More Billing Options preserves invoice discounts, reasons, approvals and split
payments. Existing credit, trade-in and owner policy controls remain available.
Totals come from the server quote, with a pink Total Payable row. Included line
discounts are labeled to avoid implying that they should be subtracted again.
Zero discount/due rows are hidden. Allocated payments are not labeled collected.
Cash/UPI/Card tiles use pink selected states; Bank Transfer and Credit remain.
Tiles use the existing payment select/events. Cash amount/change, electronic
reference/confirmation, credit due dates, eligibility and split allocations keep
their existing rules. Tiles disappear while split allocation is in use.
The pink receipt action has disabled/focus/loading states. Notes follow it and
are included in existing draft and sale payloads. CSS is scoped to New Sale.

Integration boundaries
No repository, API contract, SQL, migration or posting code changed.
Product search still uses bounded shop-specific /api/products/variants?billing=true.
Manual ambiguous matches require explicit selection. Exact scans still use
/api/scan and preserve the variant ID or physical unit ID. Search and draft edits
do not deduct stock. Product images use the existing authorized image endpoint.
All amounts still come from /api/sales/quote, including GST/pricing mode, discounts,
rounding and authorized changes. No duplicate UI pricing calculator was added.
Existing finalization validates again, uses stable request IDs and preserves
uncertain requests for exact retry. Invoice snapshots/history are untouched.
The existing sale transaction remains responsible for invoice, stock, physical
unit, payment, receivable and audit writes. Product registration, receipt posting,
SKU allocation, barcode allocation, returns and reports were not redesigned.

Limits
The existing ordinary-sale API has no standalone fitting/service-charge line.
No fake product or unsupported charge was introduced in this UI-only redesign.
Camera hardware and live bank/UPI settlement were not tested. Electronic payment
confirmation still requires staff verification; a reference is not payment proof.
The integration suite exercises returns and underlying invoice/payment records;
a full live refund, cash-closing and reporting UI audit was not performed.
No application business database was modified and no SQL needs to be run.
